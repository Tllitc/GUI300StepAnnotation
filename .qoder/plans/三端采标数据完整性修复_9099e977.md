# 三端采标工具数据完整性缺陷修复计划

## Summary

三端（Windows 根目录 / `ios端/` / `安卓端/`）各自维护独立的 `annotation_editor.py` + `data_manager.py`，在长期分头演进后产生了 **45 项有效缺陷**，其中 **9 项会不可逆破坏已交付数据**。本计划采用「**先加固断言层 → 再止血 → 后补齐**」的三阶段推进，全部为局部补丁，不做跨端架构重构。

**核心结论（用户三类症状的根因）**：

| 用户报告的症状 | 根因缺陷 | 影响端 |
|---|---|---|
| **多轮折叠** | `B20a` 轮次边界不清 `steps_data` + `_write_draft_now` 用 `rounds[-1]` 重建草稿 | Android（最严重） |
| | `B19` 续采追问指令取消分支缺失 → 整轮静默丢弃 | Android |
| | `B1/B28` answer 后取消新轮不重置工作区 | Windows / iOS |
| | `B2` `QTimer.singleShot(300)` 竞态窗口内重复落轮 | 三端 |
| | `B14` 新轮指令取消后沿用上一轮 instruction | 三端 |
| **step 顺序错乱** | `B22` 编辑历史步确认后 `current_step` 被传送到末尾 | Android |
| | `B5` coords/trajectory 条目匹配失败时位置兜底 → 静默错配 | 三端 |
| | `B12` `get_data()` 豁免名单缺 `answer_terminate` → 污染 `coordinate:[0,0]` | Windows |
| **截图错序/跳跃** | `B38` 三端序号分配语义完全不同（Windows/iOS = max+1，Android = 最小未占用） | 三端 |
| | `B10` 插入取最大号却插中间 / 删除留空洞 / 均不重命名 | 三端 |
| | `B16/B17` 删图只查 `steps_data` 不查 `rounds` → 删掉已落轮仍引用的 PNG | Android / iOS |
| **其他数据完整性** | `B30` 编辑模式下 Ctrl+Q **原地覆盖已交付 PNG**，无备份不可逆 | iOS / Android |
| | `B6` scroll 步拉框顶点永久不进 coords（校验层要求、收集层跳过） | Windows |
| | `B40/B41` 编辑写回时全量重建 `messages` / 空 coords 覆盖原文件 | 三端 |
| | `B50` iOS `save_screenshot(filename=)` 无校验 → 路径穿越写出 gui_dir | iOS |

## 阶段 0：测试断言层加固（**必须最先做，不改任何产品代码**）

> **为什么必须最先做**：`安卓端/tests/invariants.py:84-107` 的 `_expected_draft_steps` **逐行复制了产品 `_write_draft_now` 的错误重建逻辑**（`if editor._current_round_saved and editor.rounds:` → 从 `rounds[-1]` 重建）。若不先改为独立推导，修 `B20a` 时无法区分「产品修好了」与「断言跟着一起错」。同时 iOS/Android 缺跨轮截图唯一性断言，`B20a` 修好后也无从验证。

### 0.1 移植跨轮截图全局唯一性断言（T1，捕获 B1/B2/B20a 的关键）

Windows `tests/invariants.py:282,304-308` 已有 `all_seen_shots` 在**轮次循环外**做全局查重，iOS/Android 缺失。

- **`ios端/tests/invariants.py`**：在 `assert_final_json_consistency` 的 `for r_idx, traj in enumerate(trajectories):`（第 266 行）**之前**新增 `all_seen_shots = {}`；在轮内 `seen_shots` 检查旁增加跨轮检查，断言失败信息须含首次出现的 `(round, step)` 与再次出现的 `(round, step)`。
- **`安卓端/tests/invariants.py`**：在 `assert_final_json` 的 `for r in range(0, len(messages), 2):`（第 198 行）**之前**新增 `all_seen_shots = {}`；在第 212-213 行轮内 `seen` 检查旁增加跨轮检查。
- 同时在两端 `assert_files` / `assert_disk_consistency` 的内存态检查中，把「每轮 trajectory 内单射」升级为「`rounds` 全体 + `steps_data` 全体跨轮单射」：
  - `安卓端/tests/invariants.py:70-72`（当前只对单轮 `_round_screenshots([rnd])` 查重）→ 改为对 `_round_screenshots(editor.rounds)` 整体查重，并与 `steps_refs` 求交集断言为空（**除非** `_current_round_saved` 为 False，此时 `steps_data` 是未落轮的当前轮，允许与 `rounds` 无交集但自身不得与任何轮重叠）。
  - `ios端/tests/invariants.py` 的 `assert_model_consistency`（第 58-77 行）→ 在 `seen` 字典基础上追加 `rounds` 引用比对。

### 0.2 重写 Android `_expected_draft_steps` 为独立推导（T2，解锁 B20a 修复）

**`安卓端/tests/invariants.py:84-107`** 整体替换为「按语义推导」而非「复制产品逻辑」：

```
不变式：草稿的 steps_data 必须恰好等于「当前尚未落入 rounds 的步骤」，
       且与 rounds 中任何一轮的 trajectory 截图引用无交集。
```
实现要点：
- 从 `editor.rounds` 收集全部已落轮截图名 `saved_shots`；
- 期望的草稿步骤 = `[s for s in editor.steps_data if s["screenshot"] not in saved_shots]`，逐条序列化 `screenshot`/`intent`/`action_data`/`vertices`（`copy.deepcopy`）；
- 保留 `assert_draft` 第 119-120 行的空现场返回 `None` 语义；
- **新增断言**：草稿 `steps_data` 的截图集合与 `draft["rounds"]` 全部 trajectory 截图集合**交集为空**（这条断言在修复前必然失败，是 `B20a` 的直接证据）。

### 0.3 升级 Windows coords 弱断言为强断言（T3，解锁 B6 可见性）

**`tests/invariants.py:318-320`** 当前是 `if len(coords) != total_steps: assert len(coords) <= total_steps` —— 这个弱断言**恰好掩盖了 B6**（scroll 步顶点丢失导致 coords 条数少于步数被判定为合法）。改为按 action 类型强断言：
- 对每个 `coord_action_types ∪ {"scroll"}` 内的动作，coords 中必须存在对应 `(round, step)` 条目；
- 条目必须含 `vertices`（4 个有限数）与 `center`；`left_click_drag` 必须含 `start_vertices`/`start_center`/`end_vertices`/`end_center`。

### 0.4 新增编辑模式写回一致性断言（T4，捕获 B40/B41）

三端 `invariants.py` 各新增 `assert_edit_writeback_preserved(gui_dir, gui_number, before_data, before_coords, edited_round_index)`：
- `before_data["messages"]` 中**除被编辑轮对应的 user/assistant 对**以外，其余消息必须逐字节保留（含非 user/assistant 角色、末尾孤立 user 消息）；
- `len(after["messages"]) == len(before["messages"])` 且角色序列完全一致；
- 若 `before_coords` 非空，则 `after_coords` 必须非空（捕获 `B41` 空覆盖）；
- 未被编辑轮的 coords 条目必须逐字段相等。

### 0.5 新增编辑模式磁盘不可变断言（T5，捕获 B30/B11）

三端 `invariants.py` 各新增 `snapshot_dir(gui_dir) -> dict[str, tuple[int, str]]`（文件名 → (size, sha256)）与 `assert_dir_unchanged(gui_dir, snapshot)`。用于断言：编辑模式下调用 `take_screenshot()` / `delete_current_step()` / `undo_step()` 后，磁盘**零变化**。

### 0.6 新增截图序号单调性断言（T6，捕获 B38/B10）

三端 `invariants.py` 各新增 `assert_screenshot_order(editor)`：
- 遍历 `steps_data`（及 `rounds` 各轮 trajectory），从文件名 `gui_NNNNN_(\d{4})\.png` 提取序号；
- 断言**序号序列严格递增**（与 step 顺序一致）；
- 断言全局序号无重复、无空洞（`set(nums) == set(range(1, len(nums)+1))`）。
- 该断言在修复前于「插入中间步」「删除中间步」「Android 复用被删序号」三个场景必然失败。

### 0.7 修复测试夹具陷阱（T8/T9）

- **`tests/conftest.py:55-87`**：`DialogController.__init__` 声明了 `self.next_instruction = "第二轮新指令"`（第 57 行）但 `get_text`（第 86 行）实际返回 `self.getText_result_text`（默认 `"输入文本"`）→ **`next_instruction` 是死字段**。修复：让 `get_text` 返回 `self.next_instruction`，并保留 `getText_result_text` 作为兼容别名（二者同步赋值），避免既有测试（若已依赖 `getText_result_text`）失效。**改动前必须 grep 全部 Windows 测试对这两个字段的引用**。
- **`tests/conftest.py`**：新增 `editor_factory` fixture（对齐 `安卓端/tests/conftest.py:120-163` 的 `make(auto_init=...)` 形态），支持在同一测试内构造第二个 `AnnotationEditor` 以验证续采；`editor` fixture 改为基于 `editor_factory` 实现以避免重复。
- **`tests/helpers.py`**：新增 `walk_rounds(editor, rounds_spec)` 多轮走步助手（`rounds_spec` 形如 `[(3, "指令A", "click"), (2, "指令B", "click")]`），内部通过 `dialogs.next_instruction` 逐轮切换指令；新增 `open_edit_mode(editor, gui_dir, round_index)` 助手，直接调 `load_from_completed_json` 进入编辑态。
- **`ios端/tests/helpers.py`** 与 **`安卓端/tests/helpers.py`**：对称新增 `walk_rounds` 与 `open_edit_mode`（Android 用 `modal.input_text` / `modal.input_ok`，iOS 用 `dialogs.next_instruction` / `dialogs.input_ok`）。

**阶段 0 完成判据**：三端既有测试**全部仍通过**（断言层加固不应改变现有通过用例的结论，除 0.2/0.3 可能暴露既有失败——此时记录为「已被断言捕获的缺陷」，留待阶段 2/4 修复后转绿）。

## 阶段 1：止血——不可逆数据破坏（P0，最高优先）

### 1.1 编辑模式禁止一切改盘操作（B30 / B11，iOS + Android）

**已核验**：Android `take_screenshot`（`安卓端/annotation_editor.py:1700`）、`delete_current_step`（:2237）、`undo_step`（:2306）**均无 `_edit_mode` 守卫**；iOS `take_screenshot`（`ios端/annotation_editor.py:1157`）同样无守卫，且 `keyPressEvent`（:3117-3121）把 Ctrl+Q 直连到 `take_screenshot`。

**iOS 破坏链（已完整核验）**：编辑模式下 `_current_screenshot_filepath` 非空 → `take_screenshot`:1173-1174 置 `_replacing_screenshot = True` → `_do_screenshot`:1213-1225 取 `replace_name`（回退到 `steps_data[current_step]["screenshot"]`，即**原始已交付文件名**）→ `save_screenshot(..., filename=replace_name)` → `os.replace` **原地覆盖原始 PNG**。编辑模式不写 draft（:2197-2198）、`save_json_data` 直接 `open(w)` 无备份 → **不可逆**。

修复模式（三处入口统一加守卫，与 `save_current_step` 的编辑模式早退风格一致，参见 Windows `annotation_editor.py:2309-2322`）：
- `ios端/annotation_editor.py` `take_screenshot` 开头（:1159 之前）：`if self._edit_mode:` → `self.status_label.setText("编辑已完成任务时不支持重新截图")` + `return`。
- `ios端/annotation_editor.py` `delete_current_step` / `undo_step` 同样加 `_edit_mode` 早退。
- `安卓端/annotation_editor.py:1700` / `:2237` / `:2306` 对称加守卫（Android 有 `_edit_mode` 属性，已由 `load_from_completed_json` 设置）。
- 若产品上**确需**允许编辑模式重截图，则改为「另存新序号 + 写备份」，**绝不原地覆盖**；本计划默认采用禁止策略（最小风险）。

### 1.2 iOS `save_screenshot(filename=)` 路径穿越加固（B50）

**已核验对比**：Windows `data_manager.py:152-190` 的 `save_screenshot_overwrite` 做了三重校验（`os.path.basename` + 前缀 `gui_{gui_number}_` + 后缀 `.png/.jpg`），非法则 `print` + `return None`。iOS `ios端/data_manager.py` 的 `save_screenshot(gui_number, screenshot_path, filename=None)` **无任何校验**，直接 `os.path.join(gui_dir, filename)`。

修复：在 iOS `save_screenshot` 的 `filename` 分支入口，复制 Windows 的三重校验逻辑（basename 归一 → 前缀 `gui_{gui_number}_` → 后缀 `.png`/`.jpg`），非法则返回 `None` 并打印诊断。同步检查 Android `data_manager.py` 是否存在同类 `filename=` 形参，若有则同样加固。

### 1.3 删除截图前检查 rounds 引用（B16 / B17，Android + iOS）

**已核验**：Windows 由 DT-6 修复但**只查 rounds**；Android/iOS 的删图路径只查 `steps_data`：
- Android：`_on_screenshot_finished`（:1756-1760）、`delete_current_step`（:2262-2271）、`undo_step`（:2325-2343）
- iOS：`_delete_file_if_unreferenced`（:1337-1350）、`delete_current_step` pending 分支（:1891-1901）

修复模式：抽出「引用可达集」计算 —— `reachable = set(steps_data 的 screenshot) | set(rounds 各轮 trajectory 的 observation.screenshot) | ({_current_screenshot_filename} if 非空)`（口径与 `安卓端/tests/invariants.py:51-55` 的 `assert_files` 完全一致），仅当待删文件名 **不在** `reachable` 时才 `os.remove`。三端统一此口径。

### 1.4 编辑写回原子化 + 备份（三端）

**已核验**：`save_json_data` 三端均直接 `open(path,"w")` 覆盖（Android `data_manager.py:104-110`、iOS `:110-122`、Windows 同构），无 tmp+`os.replace`、无备份。而 iOS `save_screenshot` **已用** tmp + `os.replace`（可直接复用其模式）。

修复：三端 `save_json_data` 与 `save_coords_json` 改为「写 `*.tmp` → `os.replace` → 成功后返回路径」；并在**编辑模式写回**路径（`save_edited_round`）额外保留一份 `gui_N.json.bak`（仅在原文件存在时生成，覆盖式）。

### 1.5 编辑写回不得丢消息 / 不得空覆盖 coords（B40 / B41）

**已核验**：
- iOS `save_edited_round:2643-2653` 与 Android `:3180-3189` 都用 `self.rounds` **全量重建** `data["messages"]` → 原 JSON 中非 user/assistant 角色的消息、末尾孤立 user 消息全部丢失。
- iOS `:2671-2672` 与 Android `:3202-3203` 的 `if all_coords or self._original_coords_exist: save_coords_json(all_coords, ...)` → 分组结果为空但原文件存在时**写入空 coords 覆盖原文件**。

修复：
- `save_edited_round` 改为**原地替换**：`data = deepcopy(self._completed_json)`，定位被编辑轮对应的 `messages[2*round_index]`（user）与 `messages[2*round_index+1]`（assistant），仅更新其 `instruction` / `trajectory`，其余消息**保持原对象引用不动**。定位失败（messages 结构非严格交替）时**拒绝写回并报错**，不做全量重建。
- coords 写回条件收紧为 `if all_coords:`（去掉 `or self._original_coords_exist`）；当 `all_coords` 为空但 `_original_coords_exist` 为真时，打印警告并**跳过写入**，保留原文件。

### 1.6 轮次选择碰撞修复（B3）

**已核验**：三端用 `items.index(selected)` 定位轮次，摘要文本截断导致不同轮可产生相同字符串：Windows 截 30 字无步数、Android `main.py:619` 截 30 字带步数、iOS `main.py:513` 截 60 字带步数 → 同指令同前缀的多轮会**改错轮并写回**。

修复：摘要项前缀加**轮次序号**（`[第 {i+1} 轮] ...`）并把步数纳入摘要；定位改为按下标而非 `index(selected)`（`QListWidget.currentRow()` 或 `items` 的位置索引）。

## 阶段 2：轮次折叠与指令错乱（P0）

### 2.1 Android B20a 根治（**本计划最关键的单项修复**）

**已完整核验的因果链**：
1. `_save_current_round_to_list`（`安卓端/annotation_editor.py:3278-3305`）落轮后只置 `_current_round_saved = True`（:3303），**不清 `steps_data`**（对比 iOS `ios端/annotation_editor.py:2966` 明确 `self.steps_data = []`）。
2. `_write_draft_now`（:2783-2799）在 `_current_round_saved and rounds` 时从 `rounds[-1]` **重建** `steps_for_draft` → 草稿 `steps_data` 含已落轮的全部步骤。
3. 续采 `load_from_draft`（:2873-2879）见 `steps_data` 非空 → `_current_round_saved = False`，`_load_step_to_form(current_step)`，并 `return (not steps_data) and bool(rounds)` = **False** → 上层**不追问新指令**（`task_instruction` 沿用上一轮，即 B14）。
4. 用户截新图 → `_save_current_to_steps` append → `steps_data = [旧轮全部步..., 新步]`。
5. 再次落轮 → `rounds = [R1(旧步), R2(旧步 + 新步)]` → **旧轮步骤在 R2 中重复出现，跨轮截图重复引用，且 R2 用了 R1 的 instruction**。

修复（**与 iOS 对齐，删掉重建逻辑**）：
- `_save_current_round_to_list`（:3303 之后）追加清空：`self.steps_data = []`、`self.coords_data = []`、`self.current_step = 0`、`self._current_screenshot_filename = None`、`self._current_screenshot_filepath = None`、`self.screenshot_cache = None`、`self._missing_cache = {}`、`self.sidebar.rebuild_items()`（口径对齐 iOS `:2966-2979`）。
- `_write_draft_now`（:2783-2799）**整段删除** `if self._current_round_saved and self.rounds:` 的重建分支，恒用 `steps_for_draft = self.steps_data`。
- **依赖 0.2 已完成**（`_expected_draft_steps` 已改为独立推导），否则 Android 全部 7 个测试文件会失败。
- 修复后 `load_from_draft`（:2880-2883）在续采时走 else 分支 → `_current_round_saved = True` → 返回 True → `main.py:536-537` 触发 `ask_next_instruction_after_resume` 追问新指令，**B14 同步消解**。

### 2.2 Android B19：续采追问指令的取消分支（整轮静默丢弃）

**已核验**：`安卓端/main.py:541-557` 的 `ask_next_instruction_after_resume` 只有 `if ok and new_instruction.strip():` 分支（内含 `_current_round_saved = False` 复位，:554），**else 分支完全缺失** → 取消后 `_current_round_saved` 保持 `load_from_draft:2882` 设的 `True` → 后续 `_save_current_round_to_list:3279` 早退 → **用户新采集的整轮被静默丢弃**。

修复：补 else 分支，语义对齐 `安卓端/annotation_editor.py:3372-3395`（`_start_new_round` 的 `from_answer` 取消分支，该处**已正确重置**）—— 直接复用/提取为共用方法 `_reset_workspace_after_cancel()`，在取消时置 `_current_round_saved = False`、清空工作区、`sidebar.rebuild_items()`、`schedule_draft_save()`、状态栏提示「已取消，可继续截图标注」。**注意**：取消后 `task_instruction` 仍是旧值，必须清空或标记为待输入，避免 B14 复现。

### 2.3 Windows B1 / iOS B28：answer 后取消新轮不重置工作区

**已核验**：
- Windows `save_current_step:2345-2354`（answer 分支）置 `self.steps = []`（:2353）但**不清 stack 页**，随后 `QTimer.singleShot(300, lambda: self.start_new_round(from_answer=True))`；`start_new_round:3122-3129` 的取消分支在 `from_answer` 时**只改状态文案**（:3126），不调 `reset_for_new_task()`（:3206）。
- **后果已降级**：`display_step:2156` 的 `if index < 0 or index >= len(self.steps): return` 拦住了向孤儿页写入，故不会直接写错数据；实际后果为 **stack 孤儿页泄漏 + `current_step_index` 陈旧 + 用户视觉上看到上一轮残留表单/截图**。

## 阶段 3：截图序号与文件生命周期（P1）

### 3.1 B38：统一序号分配语义（三端签名/语义全不同）

## Rejected Alternatives

### 拒绝方案 A：抽取三端共用纯函数模块（`round_writer` / `screenshot_naming` / `coords_rounding`）
**理由**：
1. **打包结构不支持**：三端各自独立 PyInstaller 打包（`GUI长步骤采标工具-Windows.spec` / `ios端/GUI长步骤采标工具-iOS.spec` / `安卓端/GUI长步骤采标工具-Android.spec`），无共享包、无 `__init__.py`，三端 conftest 各自 `sys.path.insert(0, 产品目录)`。抽公共模块需同步改 3 个 spec 的 `hiddenimports`/`datas` 与 3 套 `sys.path` 注入逻辑，**改动面远超收益**。
2. **coords schema 统一会触碰已交付数据**：三端 schema 已分化（Windows 纯数组无 `_version` / iOS 纯数组 + `_version="3.1"` / Android `{"version":"3.0","coords":[...]}`），下游训练数据管线的兼容性**未知且不可验证**。强行统一的回归风险不可控。
3. **对核心症状无帮助**：用户报告的「多轮折叠 / step 错序 / 截图错序」中 90% 是**逻辑遗漏**（缺守卫、缺分支、缺 deepcopy、缺 `delete_draft`），不是架构问题。方案 A 覆盖率约 40%，且覆盖的是**不产生数据错误**的结构性分歧（B38/B39/B34/B46 只导致跨端不可移植）。

**采纳的部分**：方案 A 的「统一不变量断言层」思想 —— 即阶段 0 的 T1~T6（把 Windows 独有的跨轮截图唯一性断言移植到 iOS/Android、重写 Android `_expected_draft_steps`、升级 Windows coords 弱断言）。这是方案 A 中**成本最低、收益最高**的部分，且不触碰产品代码。

### 拒绝方案 B：iOS 截图异步化（对齐 Android `_capture_worker`）
**理由**：
1. **不产生数据错误**：iOS `_do_screenshot:1188` 同步阻塞主线程只影响 UX（卡 UI），**不导致轮次折叠 / 序号错乱 / 数据丢失**。用户诉求是数据完整性。
2. **改造成本高且引入新竞态**：需引入 QThread + 信号 + `_screenshot_seq`（对齐 Android `:1700-1780`），并改 `ios端/tests/helpers.py:capture`(41-54，当前依赖 `_wait_until(not _screenshot_in_progress)`) 与 `test_recapture.py`(383 行) / `test_insert_capture.py`(645 行) 共 1000+ 行测试。异步化会让 B2 类 `singleShot(300)` 竞态**更难复现和定位**。
3. **收益可由 2 行达成**：B15（stack 页泄漏，方案 B 中唯一的真实数据/资源问题）用 `setParent(None)` + `deleteLater()` 即可修复（见 2.4），无需异步化。

**采纳的部分**：仅 B15 的极简修复（2.4）。侧栏增量刷新（B47，iOS `confirm_step` 编辑模式走 `sidebar.rebuild_items()` 全量重建，300 步性能问题）**降级为可选优化，不列入本计划**——它是性能问题，不影响数据正确性。

### 拒绝「一次性重写三端为单一代码库 + 平台适配层」
**理由**：三端 `annotation_editor.py` 分别为 3317 / 3136 / 3472 行，合计近万行，且 UI 交互模型根本不同（Windows 是 `QStackedWidget` + 每步一个 `StepEditorWidget` 的多页模型；iOS/Android 是单表单 + `current_step` 下标 + `_restore_step_to_ui` 的单页模型；Android 还有 `ScrcpyEmbedWidget` HWND 嵌入与 `_overlay_to_phone_coords` 坐标映射）。重写周期内**既有 ~5000 行测试全部失效**，且用户当前有已交付数据需要维护，不能接受长周期不可用窗口。

### 拒绝「删除 B5 的位置兜底匹配」
**理由**：位置兜底（Windows `_find_coord_entry:2788-2797`、iOS `:2458-2459`/`:2587-2588`、Android `:3030-3032`/`:3165`）虽然可能静默给出错误 vertices，但**删除它会让历史上已错位的 coords 文件完全无法打开编辑**（匹配失败即返回 None，用户连修正的机会都没有）。改为「保留兜底 + 显式告警 + 写回前汇总确认」（4.4），在可用性与正确性之间取得平衡。

### 拒绝「统一三端 `_missing_cache` 类型（B46）」
**理由**：iOS 用 `list`（`get_cached_missing` 用 `len()`/索引）、Android 用 `dict`（`.get(index)`），二者**各自内部自洽且不产生数据错误**，只是跨端阅读成本高。统一需改动 iOS `_on_validation_debounced` / `revalidate_all_missing` / `sidebar.set_missing` 全链路，属于纯风格重构，**在数据完整性修复计划中不应占用风险预算**。记录为技术债。

### 拒绝「统一三端 draft schema（B34）」
**理由**：Windows 用 `current_steps`/`coords_entries`/`rect_info`/`selection_type`，Android/iOS 用 `steps_data`/`current_step_index`，且 `load_draft_from_dir` 签名不同（Android 是 `(draft, err_type)` + `DRAFT_ERR_CORRUPT/NOT_FOUND` + `is_task_completed`/`has_screenshots`；Windows/iOS 单值）。draft 是**端内私有中间态**，从不跨端交换（用户在 Windows 采的数据不会拿到 Android 续采），统一无实际收益，且会破坏全部既有 draft 的向后兼容（用户机器上现存未完成任务的草稿将全部无法恢复）。记录为技术债。
