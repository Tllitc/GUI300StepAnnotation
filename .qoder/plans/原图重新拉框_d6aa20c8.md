# 原截图重新拉框（三端 + 测试）

## Summary

**需求**：编辑已完成任务时，若只想改某一步的动作拉框而不必重现画面重新截图，则直接在**磁盘已保存的原截图**上重新拖框。

**核心事实（决定方案安全性）**：磁盘 PNG 存的是**无标记原始截图**，红/绿框都是预览时按物理像素重绘的（Windows `build_marked_preview`、iOS `restore_vertices`、Android `ScreenshotCanvas.set_screenshot(path, vertices)`）。因此"重新拉框"**只需改内存中的 `rect_info`/`vertices` + 坐标输入，不写任何图片文件**，天然规避 `save_screenshot_overwrite` 的原子覆盖、文件名校验、误删他轮截图等风险。

**统一交互约定（三端一致）**
| 项 | 决策 |
|---|---|
| 入口 | 工具栏新增按钮 **「在原图上重新拉框」**（`#9C27B0`），初始 `hide()`，仅在编辑已完成任务时显示 |
| 弹窗 | 独立窗口/对话框，背景 = 该步磁盘原截图 |
| 旧框 | **打开即清空**（不叠加旧框，必须重新画一个） |
| 确认 | Windows：`Ctrl+S`；iOS/Android：弹窗内「应用新框」按钮 |
| 取消 | Windows：`Esc`；iOS/Android：`Esc`/「取消」→ 旧框原样保留 |
| 坐标微调 | **不做**（用户明确不需要） |
| 落盘 | 只改内存，必须再点「保存修改」才写 JSON/coords |
| swipe/scroll | 只重画**起点框**，终点 `coord2_*`/`end_coord_*` 保持原值；状态栏需明确提示 |

**不改动**：`main.py`（仅为组装壳）、`macos端/`（不在交付范围）、`data_manager.py`（三端 `load_screenshot(gui_number, filename)` 已具备所需能力）。

## 风险与规避

| 风险 | 规避 |
|---|---|
| **门闩泄漏**：弹窗异常关闭导致 `_capture_in_flight` 永久 True，后续所有采集入口死锁 | `on_relabel_completed` **第一行**无条件复位；`_is_closing` 次行早退；closeEvent 元组含 `relabel_window` 兜底关闭；测试 #5 断言复位 |
| **DI-8 不变量破坏**（B2：多条采集入口共用门闩） | 重新拉框复用 `_capture_in_flight`/`_screenshot_in_progress` 同一标志，**不新增并行标志** |
| Windows 背景模式空选区被当成"全屏截图"，产生 `selection_type="fullscreen"` + 空 `rect_info` 污染该步 | `confirm_selection` 首分支按 `background_pixmap is not None` 改发 `"cancelled"`；测试 #7 覆盖 |
| `scale_factor` 语义漂移（抓屏=物理/逻辑屏幕；背景=原图/显示图） | 两模式统一定义为「输出像素 ÷ widget 逻辑像素」；`_setup_background` 中 offset 恒为 0，窗口尺寸严格等于 `full_pixmap` 尺寸 |
| HiDPI 下预览停留在缩放图、或框位与坐标不符 | 回填后调用 `_on_editor_preview_resize`（第 2185 行）从磁盘原图重绘；`build_marked_preview` 用物理像素画框，与 `rect_info` 同口径 |
| `handle_selection` 无 `box_count==2` 复位 → 画满两框后无法重画 | 不改该行为（影响正常采标）；用弹窗内提示文字引导「Esc 清空重画」，并在交付说明中标注为已知限制 |
| swipe/scroll 语义误改（把终点也覆盖掉） | 三端一致：**只改起点框**，终点保持；状态栏显式提示；测试 #10 覆盖。iOS/Android 打开弹窗前先 `_cancel_swipe_measurement`/`_cancel_scroll_measurement`，避免 `_scroll_references`/`_scroll_extra_screenshots` 被污染 |
| 意外写盘（覆盖 PNG / 生成 draft / 新增文件） | 新链路**完全不调用** `save_screenshot_overwrite`、`save_screenshot`、`schedule_draft_save`；测试 #1 用字节比对 + `snapshot_listing` 集合等值断言 |
| 弹窗生命周期（`WA_DeleteOnClose` 导致悬空引用 / 关窗后自动写回被遮挡） | 显式**不设** `WA_DeleteOnClose`；`parent=self`；closeEvent 中先 `close()` 弹窗再执行本端自动写回 |
| 三端代码漂移（撤销、坐标、锁机制各异） | 每端各自实现并跑各自 tests 目录；不做跨目录共享模块（会破坏 3 份 PyInstaller `.spec` 的打包边界） |

## Rejected Alternatives

1. **iOS 直接在主预览画布拖框（不弹窗）** —— `ScreenshotCanvas.mousePressEvent` 本就无编辑态门禁，看似零改动。否决：无法实现"打开即清空旧框"的明确心智与独立「应用/取消」语义；且会让正常采标流程中的误拖框直接改数据，风险面反而更大。
2. **Windows 复制一份独立的 `ReLabelCaptureWindow`** —— 隔离彻底。否决：需重复约 350 行（双框归并、箭头 `atan2` 绘制、物理换算、ESC/Ctrl+S），与正常截图窗永久漂移；改为给现有类加 `background_pixmap=None` 参数，`mouse*`/`paintEvent`/`handle_selection`/`confirm_selection` 主体零改动。
3. **Windows 复用「重新截图 + 覆盖保存」现有链路** —— 改动量最小。否决：需设备/屏幕重现完全相同画面，且 `save_screenshot_overwrite` 会**不可逆覆盖磁盘原图**，与本需求"不动图片"的诉求正好相反。
4. **弹窗内叠加旧框作为参照** —— 便于对齐微调。否决：用户明确选择「直接清空旧框」。
5. **坐标输入框手动微调框位** —— 用户明确「暂不需要」，且三端 `coord_*_input` 已有各自的校验/联动逻辑，改动会牵连 `validate_step_at` 与 `_collect_coords_entries`。
6. **Android 用 `OverlayWidget` 在 scrcpy 实时画面上重画** —— 复用现有拉框交互。否决：实时画面 ≠ 该步历史截图，且依赖设备在线/adb 可用，与"在原截图上编辑"的语义不符。
7. **三端抽公共模块（一份实现共享）** —— 消除重复。否决：三端目录各自独立打包（`GUI长步骤采标工具-{Windows,Android,iOS}.spec`），跨目录 import 会破坏 PyInstaller 采集与既有测试隔离；且三端坐标/锁/撤销语义本就不同，强行统一会引入隐性行为变更。
8. **为性能常驻缓存背景 pixmap / 预生成缩略图** —— 方案B主张。否决：编辑态按需 `load_screenshot` + 既有缩略图 LRU（`_cache_key` 已含 `rect_info`）足够；新增缓存层要扩大 closeEvent 清理面与失效逻辑，收益不匹配风险。
